# 組み分けぼうし

複数回のグループ分けで、同じ人同士の組み合わせが偏ることをできるだけ防ぐWebアプリです。

## 1. サービス概要

「組み分けぼうし」は、懇親会・勉強会・ゲームなどで使うグループ分けアプリです。  
名簿と組数を入力すると、通常のランダム組み分けに加え、過去に同じ組だったペアをできるだけ避ける「組み分け防止モード」を利用できます。  
参加者がより多くの人と話せる機会をつくり、交流の偏りを減らすことを目指します。

## できること（機能一覧）

 メンバーを入力し、組数をしていすると、組み分けを行います。
 2回目以降は、同じメンバーと被らないように、被り防止機能をONにできます。

処理の流れ
現在のメンバーをシャッフルする
指定されたグループ数にメンバーを振り分ける
作成されたグループの組み合わせを確認する
過去の組み合わせと重複していないか判定する
重複している場合は、別の組み合わせを作り直す
過去にない組み合わせができたら、その結果を採用する
採用した組み合わせを履歴として保存する

これにより、組み分けを繰り返すたびに、できるだけ前回までとは異なるメンバー同士の組み合わせを作ることができます。

※組み合わせの上限

　メンバー数とグループ数によっては、作成できる組み合わせには限界があります。
　すべての組み合わせを使い切った場合、それ以上「過去と重複しない組み分け」を作ることはできません。
　その場合は、無理に組み分けを続けるのではなく、ユーザーに「これ以上新しい組み合わせを作れない」ことを知らせ、通常の組み分けを続けるか、履歴をリセットして最初からやり直すかを選択できるようにします。

目的

この機能の目的は、単純に毎回ランダムに組み分けるのではなく、
「できるだけ同じメンバー同士が一緒にならないようにする」
ことです。

そのため、複数回のグループ分けを行う授業・ゲーム・イベントなどで、メンバー同士の組み合わせが偏ることを防ぐことができます。


## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

懇親会でグループ分けアプリを使った際、前回と同じ人と同じグループになることがありました。  
一方で、まだ話したことのない人とは別のグループになってしまい、「せっかく交流の場に来たのに、新しい人と話す機会が少ない」と感じました。

グループ分けは短時間で決める必要があるため、主催者が過去の組み合わせをすべて覚えたり、手作業で調整したりするのは現実的ではありません。そこで、楽しさを保ちながら組み合わせの偏りを抑えられる仕組みを作りたいと考えました。

### 2-2. なぜそれが気になったのか

私は、懇親会や勉強会では、普段関わらない人と話すことに価値があると考えています。  
同じ人との会話も大切ですが、毎回同じ組み合わせになると、参加者同士のつながりが広がりにくくなります。

「全員に公平に、新しい会話のきっかけがある状態」を大切にしたいという思いが、この課題を気にした理由です。


## 3. 課題の整理

### 3-1. 表に見えている困りごと

ランダムな組み分けを繰り返すと、同じ人同士が何度も同じグループになることがあります。  
その結果、まだ会話したことのない参加者と関わる機会が失われてしまいます。

### 3-2. 本当に解決したい課題

- なぜ困るのか？  
  同じ組み合わせが続くと、交流相手が固定されるためです。

- なぜ交流相手が固定されると困るのか？  
  新しい会話や関係が生まれにくくなるためです。

- なぜ新しい関係が生まれにくいと困るのか？  
  懇親会や勉強会に参加する価値である「参加者同士の交流」が十分に得られなくなるためです。

**本当に解決したい課題：**  
複数回のグループ分けでも、参加者ができるだけ多くの人と関わり、自然に会話できる機会をつくること。

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー（例えばこんな人）

#### 年齢設定

- 年齢：20代後半
- 想定ユーザー：プログラミングスクールの受講生で、定期的な懇親会や勉強会のグループ分けを担当する人
- 理由：同じコミュニティで複数回交流するため、前回までの組み合わせを考慮する必要があるからです。

#### 生活・状況設定

- 生活・状況：平日は学習や仕事をし、週末やイベント時に参加者10〜20人ほどの交流会を企画・運営している
- 理由：当日の限られた時間で組み分けを決める必要があり、手作業での重複確認が負担になるためです。

#### 環境設定

- 環境：参加者の名前をスマートフォンまたはPCで入力し、その場で結果を共有する
- 理由：専用ソフトや複雑な設定なしで、名簿入力から組み分けまでを短時間で完結させる必要があるためです。

### 4-2. 自分とユーザーの距離

- 自分自身

懇親会で同じ人と組になる経験をし、交流の偏りを感じたことがこのアプリの出発点です。参加者として感じた不便さを、主催者も解消できる形にしたいと考えています。

### 4-3. 実際に使われる可能性について

最初に使ってくれそうなのは、勉強会・懇親会・社内イベントなどで、複数回グループ分けを行う主催者です。

参加者から「前回と違う人と話したい」と言われたときや、2回目以降のグループ分けをするときに、このアプリを思い出すことを想定しています。

現在は、くじ引き・手作業・一般的なランダム組み分けツールが代替手段です。しかし、それらでは過去の組み合わせを考慮しにくいため、「できるだけ新しい人と話せる」という価値が利用理由になります。

### 4-4. 導入・継続の流れ

1. 主催者が懇親会や勉強会で複数回のグループ分けを行う必要が生じる  
2. 名簿を入力、またはCSVから取り込む  
3. 組数と組名を設定し、通常モードまたは組み分け防止モードを選ぶ  
4. 結果を表示し、必要に応じてCSVとして出力する  
5. 次の組み分けでは同じセッション内の履歴を利用し、過去のペアをできるだけ避ける

複数回のグループ分けを行うイベントほど価値を感じやすく、履歴表示によって過去の結果も確認できます。

## 8. このアプリの懸念点とその対策

### 懸念点①：回数を重ねると完全に新しい組み合わせを作れなくなる

- 何が問題になりそうか：参加人数と組数が決まっているため、すべてのペアを避け続けることはできない
- なぜそう思うか：組み分けを繰り返すほど未使用のペアが減るため
- そのために考えている対策：1,000回の試行から過去のペアが最も少ない結果を選び、すべてのペアが使用済みになった場合は、履歴をリセットするか通常モードに切り替えられるようにする

### 懸念点②：ブラウザを閉じると履歴が失われる

- 何が問題になりそうか：現在はRails Sessionに履歴を保存しているため、別端末や別ブラウザで履歴を引き継げない、ビジネス等でアプリを使用する場合には保存できたほうが便利と考えられる
- なぜそう思うか：現段階ではアカウント機能とイベント単位の永続保存などの機能は実装していないため
- そのために考えている対策：ログイン機能とDB保存を追加し、イベントごとに履歴を管理できるようにする

組み分け履歴の保存について
今回は、DBは作らずRailsのsessionに保存することにする。DBをつくると永久にサーバーに保存されてしまうため負荷がかかるのと、組み分け履歴は際限なく増え続けるため。sessionとして保存する履歴は、理論上の被り防止回数上限が終了したら、または任意リセットのときに履歴を削除することにした。

組み分けは、なるべく違う人と会うように設定しているが、回数を重ねると可能な組み合わせが減っていくため、理論上の限界回数がある。
しかし、単純な割り算では求めることができない。端数やその調整で同じ人と組み分けされることがあるため。そのため理論上の上限がきたら判定しアクションを起こす必要がある。

上限について
基本ルール：履歴から完全に新しい組み合わせをさがす。しかしこれには穴があり、人数をグループ数で割り切れないときにこのルールだとペアになっていない状態で上限に達して終了してしまう。
そこで、上限ルールを二重にする。第一条件は上記として、その時点の上限にきたら、「全員と一度ペアを組んだのかを履歴から確認し消化する」を第二の条件に最終上限とした。

----------------------

1000回試す
 ↓
一番良かったものを保存（best_score）
 ↓
最後に返す　被りはnil

これだと上記のような穴ができる

best_groups = nil（被りなしでは作れないとき）
best_score = -1　（最善）

としていたが、この理由により削除とした

----------------------

このルールなら終盤は被りは多少出るが、全員と組になることができる。
アプリ内では説明は省略するため、終盤には「被りがでている」と思うかもしれない。が、「なるべく被らないようにする魔法」と説明しているので良しとした。

ルートの分岐とモード選択によって複雑化してしまいエラーが増えたので、内容整理をした。ノーマルモードをfalse組み分け防止モードをtureとしbooleranでON・OFFを管理することにした。これにより簡略化できルートもわかりやすくなった。

組み分け上限の回数を把握しやすくするために、結果画面に現在の回数を表示させた。
最初はカウントで行っていたがブラウザの影響で回数と履歴に差がでることがあったので、session履歴を取り込んでカウントすることにした。ノーマルモードでは履歴がないので、現状のカウントとした。
